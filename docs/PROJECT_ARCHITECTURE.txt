================================================================================
LOCOBOT_PROG — FULL PROJECT ARCHITECTURE
Thesis project: LoCoBot (mobile base + WidowX-250s arm) pick-and-place in
Gazebo, driven by a VLM agent, built on ROS Noetic + MoveIt.
Generated by walking every file in the package and verifying its role against
the actual code (imports, rospy.Service/ServiceProxy calls, launch files) —
not from memory or design docs. First written 2026-09-28; refreshed
2026-10-05 after the YOLO detector was fine-tuned/retrained twice, detection
smoothing was added, the target-class alias system was replaced, and three
grasp-reliability fixes (orientation routing, a premature-weld stall gate,
and the gripper-weld plugin's own trigger mechanism) were traced and fixed.
================================================================================


================================================================================
PART 1 — THE BIG PICTURE
================================================================================

This package runs as 7 separate ROS processes ("nodes"), each doing exactly
one job, talking to each other ONLY through typed ROS services and topics
(never raw Python references, even between two classes that happen to share
a process). This is a deliberate, repeatedly-reaffirmed design rule in this
project: "one service per action, small classes, no JSON-blob dispatch."

The 7 live nodes (all under the "locobot" namespace):

  1. yolo_detection_node   — camera in, 3-D object detections out (JSON)
  2. detection_shim        — converts that JSON into a typed ROS message
  3. world_model           — perception fusion + grasp planning + task
                             sequencing (TWO classes, one process — see below)
  4. arm                   — the only MoveGroupCommander; executes grasps
  5. navigation            — the only cmd_vel publisher; drives the base
  6. vlm_agent             — talks to a local LLM (Ollama) and decides what
                             high-level action to take
  7. set_camera_angle      — one-shot: points the camera at the table, then
                             exits

Everything else in scripts/ is a PURE PYTHON MODULE imported by one or more
of these 7 — never launched directly, never a ROS node of its own. This
split (thin ROS "node" file + pure, unit-testable logic modules) is
consistent across the whole codebase and is why the test/ folder can test
grasp geometry, the grasp planner, and PID-adjacent logic completely
offline, with no ROS or Gazebo running at all.

Rough data flow for one pick-and-place, start to finish:

  Gazebo camera images/depth
        |
        v
  yolo_detection_node  --(JSON string topic)-->  detection_shim
        |                                              |
        |                                    (typed DetectionArray)
        |                                              v
        |                                       world_model (WorldModelNode
        |                                       half): fuses detections into
        |                                       a running model of the scene
        |                                              |
        |                    VLM agent  --(service calls)-->  world_model
        |                    (vlm_agent_node.py)         (TaskOrchestrator
        |                                                 half): sequences
        |                                                 navigate -> pre-
        |                                                 grasp -> grasp ->
        |                                                 place, calling out
        |                                                 to navigation_node
        |                                                 and arm_node as
        |                                                 needed
        v
  navigation_node (drives the base)      arm_node (the only MoveGroupCommander;
                                          executes the two-phase grasp)

The VLM agent is the only thing that decides WHAT to do next at the
highest level ("try to pick up the bottle again"); every one of the
actual steps (where the object is, where the arm should stand, whether
the jaws are centred, how far to squeeze) is plain, deterministic,
carefully-verified Python code with no AI involved. The VLM is a thin
policy layer sitting on top of a fully classical robotics stack.


================================================================================
PART 2 — THE 7 NODES, ONE BY ONE
================================================================================

--------------------------------------------------------------------------
2.1  yolo_detection_node.py   (scripts/yolo_detection_node.py)
--------------------------------------------------------------------------
Role: the only thing that looks at raw pixels. Runs a YOLOv11 detector +
a hand-written 3-D back-projection (from a separate, external "YOLO3D"
toolkit checked out alongside this workspace, imported via a relative
sys.path hack at the top of the file) to turn 2-D boxes into 3-D
positions and rough dimensions.

THE DETECTOR ITSELF IS NOW FINE-TUNED, NOT STOCK COCO. Two retrains since
this doc was first written: finetune1 (2026-10-02, 591 frames, 4 classes —
bottle/tea_box/can_coke/ball) then finetune2 (2026-10-03, 1310 frames, 5
classes, adding table — a fresh retrain from the stock yolo11s.pt
checkpoint, not a resume, since the detection head's output size is fixed
per training run). Training data comes from auto_label.py (scripts/
auto_label.py): a collector that spawns objects in Gazebo and derives
exact, pixel-tight bounding boxes from Gazebo's own ground-truth model
poses + the known camera projection, instead of a human labelling images —
see test/test_auto_label.py for the geometry this rests on. The checkpoint
is loaded explicitly (`ultralytics.YOLO(path)`, swapped into the YOLO3D
library's own ObjectDetector after construction) via the yolo_model launch
arg, now pointing at the finetune2 weights. Held-out validation: mAP50-95
0.984 overall, 0.995 on the table class specifically. Remaining gap:
"person" has no trained examples (no person model exists in any current
world) and is still only ever COCO-recognized if it appears at all.

What it does, concretely, on every synchronized RGB+depth frame:
  - Runs the detector (with multi-object tracking) on the RGB image.
  - Smooths each tracked object's position/size/orientation through
    _TunedBBox3DEstimator, a subclass of the YOLO3D library's own
    BBox3DEstimator that only overrides its Kalman filter's measurement-
    noise constants (R) — the library's defaults were tuned for street-
    scene-scale driving footage, an order of magnitude larger than this
    project's tabletop distances, so unmodified they under-trusted every
    real measurement. See test/test_yolo_smoothing.py.
  - Keeps only detections whose class is in ~target_classes, plus
    whatever's in SCENE_CLASSES ({"dining table", "table", "person"} —
    always kept, needed for scene modelling regardless of what the user
    is trying to pick up). ~target_classes, when left at its default empty
    list, is now auto-derived from EVERY yolo_labels entry across the
    whole catalogue (config/objects.yaml, via resolver.ObjectCatalog) —
    this replaced an earlier design where the real publish filter was a
    separate, independently-hand-maintained launch-file list that could
    (and once did) silently omit a newly-catalogued object's label,
    making it undetectable even though a separate, purely cosmetic
    is_target alias map (see below) suggested it should work.
  - Samples the object's depth (median of the INNER 50% of its bounding
    box, to dodge edge pixels and depth holes).
  - Applies a measured correction: the sampled depth is the object's FRONT
    surface, not its centre axis, so it pushes the point deeper along the
    camera ray by the estimated radius before back-projecting — without
    this, every grasp point was measured ~1 radius short (a documented
    -3.9 cm bias for the bottle).
  - Computes width/height directly from the pixel box + depth (pinhole
    geometry); for object depth (front-to-back), objects known to be
    round (bottle/vase/cup/wine glass/bowl) get L = W (a round object's
    depth along the approach equals its width); everything else falls
    back to a per-class prior table (DEFAULT_DIMS, from the YOLO3D repo).
  - Transforms the point from the camera's optical frame into
    <robot>/base_link via TF, at the frame's own timestamp.
  - Estimates a rough orientation ("theta_ray") from the viewing angle —
    refined later, downstream, by detection_shim.py (see 2.2).
  - Publishes ALL of this, per frame, as one JSON string on
    /locobot/locobot_prog/detections_3d (std_msgs/String) — NOT a typed
    ROS message. It also republishes the annotated debug image.
  - Flags is_target = (class_name == target_object) OR (class_name is in
    a hardcoded per-target alias list, _ALIAS_MAP). Now that the detector
    is fine-tuned on this project's own class names, this alias map is
    mostly a leftover from the stock-COCO era (bottle -> "vase", tea_box
    -> "remote", etc.) — harmless, since a fine-tuned detection's
    class_name already matches directly, but not yet removed.

This node is explicitly "untouched" by the rest of the pipeline's several
refactors in the sense that its STRUCTURE (detect -> smooth -> filter ->
back-project -> publish JSON) hasn't changed — every fix since has been
either a config/weights swap (the fine-tunes) or additive (the smoothing
subclass), never a rewrite of its control flow, to avoid destabilising
the one component with a real ML model inside it.

--------------------------------------------------------------------------
2.2  detection_shim.py   (scripts/detection_shim.py)
--------------------------------------------------------------------------
Role: adapter. Converts yolo_detection_node's loosely-typed JSON string
into the typed locobot_prog/DetectionArray message the rest of the system
expects, WITHOUT touching yolo_detection_node.py itself.

  /locobot/locobot_prog/detections_3d  (String, JSON)
        |  + one refinement step (see below)
        v
  /locobot/locobot_prog/detections     (DetectionArray) -> world_model

It also applies ONE piece of real logic: for each detection it calls
locobot_geometry.estimate_grasp_orientation() (see 3.x below) to refine
the raw viewing-angle-based yaw into a real image-derived orientation
(contour fit + physical-symmetry short-circuit for round objects +
180-degree flip resolution), before publishing. Without this shim, the
downstream code would only ever see the cruder raw yaw.

--------------------------------------------------------------------------
2.3  world_model_node.py   (scripts/world_model_node.py, 883 lines — the
     biggest file, TWO classes in ONE process)
--------------------------------------------------------------------------
This is the load-bearing file of the whole project. It contains two
classes that are architecturally separate (they only talk to each other
via ROS service calls, exactly like they would if they were two
different processes) but are started in the SAME process for RAM reasons
(explained in 2.3.3).

  2.3.1  WorldModelNode  — "what is where" (perception half)
  --------------------------------------------------------
  Owns:
    - self.model : a world_model.WorldModel instance — the running fused
      picture of the scene (see 4.1 below), fed every incoming detection
      frame.
    - A short rolling buffer of raw depth images (~3s, throttled to 10Hz)
      used ONLY by the grasp planner (~plan_grasp), so it can back-project
      real depth pixels instead of trusting a bounding box.
    - The odometry-held target cache (target_odom_cache.TargetOdomCache) —
      "where is the target NOW, even if the camera can't currently see it
      (e.g. the arm is in the way)".

  Services it SERVES (all under /locobot/world_model/...):
    ~get_scene      (GetScene)      the full scene: objects, what blocks
                                     the approach, the current "zone", the
                                     table model, collision boxes, and
                                     (optionally) a rendered bird's-eye
                                     view image.
    ~get_target     (GetTarget)     every source of where the target is
                                     (fresh lock / recent median / map
                                     reprojection / calibrated size).
    ~target_memory  (TargetMemory)  MEASURE / REPROJECT / FORGET / SET —
                                     the odometry-held reference used by
                                     the arm's contact-safety check when
                                     the camera can't see the object.
    ~plan_grasp     (PlanGrasp)     the REAL depth-image grasp planner
                                     (see 4.3, grasp_planner.py). Measures
                                     the true table height from the depth
                                     frame, finds the object's real width
                                     profile, and returns a full grasp
                                     plan — or declines, with a reason.

  Subscribes to:
    /locobot/locobot_prog/detections        (DetectionArray, from the shim)
    /locobot/camera/color/camera_info       (to get the camera intrinsics K)
    /locobot/camera/aligned_depth_to_color/image_raw  (raw depth, buffered
                                                        for plan_grasp)

  Publishes:
    a "live" bird's-eye-view debug image on a timer, for rqt_image_view.

  2.3.2  TaskOrchestrator  — "what to do about it" (the actual pick logic)
  ------------------------------------------------------------------------
  This class is the WHOLE pick-and-place sequencer. It is a client of
  almost everything else in the system (it holds ServiceProxy objects to
  world_model's own services, to arm_node's services, and to
  navigation_node's services), and it exposes exactly two services of its
  own, under ABSOLUTE names (not namespaced under "~task", because the
  VLM agent needs to find them at a fixed, known path regardless of which
  node they end up living in):

    /locobot/task/get_object   (GetObject)    the full pick-and-place:
                                               observe -> navigate ->
                                               pre-grasp -> grasp -> place.
                                               This is the VLM's main tool.
    /locobot/task/navigate_to  (NavigateTo)   drive to the standoff in
                                               front of an object WITHOUT
                                               grasping. The VLM's other
                                               tool.

  Its main method, _pick_and_place(), is the heart of the project:
    1. Tuck the arm to camera_clear so the camera has an unobstructed view.
    2. Read the target's position (median of recent detections, or the
       last lock, or a map reprojection — see target_state.py).
    3. Cache that position in odometry (TargetMemory MEASURE) — the arm
       will occlude the camera in a few seconds, so this is the only
       chance to remember "where it really is" before that happens.
    4. Choose a grasp plan: try the REAL depth-based planner
       (~plan_grasp) first; silently fall back to the formula-based
       baseline_plan() (grasp_geometry.py) if it declines or the target
       isn't in the current frame. See PART 4 for exactly how this
       works.
    5. PRE-GRASP: call arm_node's ~execute_pregrasp with that plan (the
       whole scene, including the target itself, is added as an
       obstacle). If it fails, correct the base's position once
       (navigation_node's ApproachTarget CORRECT mode) and retry.
    6. Base-tilt correction (_settled_shift): once the arm is loaded at
       the standoff, the mobile base tips slightly under its own weight.
       This method re-measures the target via the odometry cache and, if
       the shift is bigger than noise, RE-TAKES THE WHOLE PRE-GRASP at
       the corrected pose (not just a patch to the final approach — see
       the session notes in memory for why a partial fix broke on a
       wrist singularity).
    7. GRASP: call arm_node's ~execute_grasp with the current best plan
       and the odometry-reprojected object position (the camera is
       blind here). arm_node straddles the jaws around the object,
       verifies contact, closes, and lifts.
    8. PLACE: lower the object back down at the SAME (x, y) it was
       picked from (the arm is already positioned right above it), at
       the height it was grasped from.
    9. Build a human/VLM-readable description of what happened and
       return it, along with a bird's-eye-view image if one was produced.

  2.3.3  Why one process, two classes (not two nodes)?
  ------------------------------------------------------
  An earlier version of this project (documented in this project's own
  history/memory, "architecture rework attempt 1") split perception and
  task logic into fully separate ROS nodes. That rework was REVERTED: it
  measured a real +324 MiB RSS jump on the development machine (a machine
  with ~7.4 GB total RAM, already running Ollama's ~2.7 GB model) and made
  the whole machine freeze. The current design keeps the RAM profile of
  ONE process while preserving the architectural discipline of "talk only
  through typed services" — TaskOrchestrator calls WorldModelNode's
  services exactly as if it were a separate process, it just happens not
  to pay the OS-level cost of actually being one.

--------------------------------------------------------------------------
2.4  arm_node.py   (scripts/arm_node.py)
--------------------------------------------------------------------------
Role: THE ONLY MoveGroupCommander in the whole system. Every arm/gripper
motion, for any purpose, goes through this one process. (The file's own
docstring explains why: a second MoveGroupCommander would double the
planning-scene subscriptions, and a second PlanningSceneInterface could
race this one on collision-object diffs — this node adds/removes the
target mid-grasp, so a competing writer would make the two-phase
collision semantics nondeterministic.)

Services it serves (/locobot/arm/...):
    ~set_arm_pose       (SetArmPose)       move to a named joint pose
                                            (camera_clear / grasp_ready /
                                            lift) — raw joint-space, no
                                            collision checking.
    ~set_gripper        (SetGripper)       fully open or fully close.
    ~get_gripper_state  (GetGripperState)  current finger position and
                                            whether it looks like it's
                                            holding something (manual/
                                            debug use — not called by the
                                            automated pipeline, which gets
                                            gripper width from
                                            ExecuteGrasp's own response
                                            instead).
    ~execute_pregrasp   (ExecutePregrasp)  PHASE 1 of a grasp: add every
                                            object (target included) as a
                                            collision obstacle, move to the
                                            standoff, verify by measuring
                                            the ACTUAL end-effector pose
                                            against the commanded one.
    ~execute_grasp      (ExecuteGrasp)     PHASE 2: remove the target
                                            obstacle, move straight in,
                                            verify the open jaws straddle
                                            the object (using an odometry-
                                            supplied position — the camera
                                            is blind here), close, attach,
                                            lift.
    ~execute_place      (ExecutePlace)     lower and release.

Internally this file is intentionally thin — it converts ROS messages to
and from plain Python dicts/tuples (_plan_to_dict, _box_to_dict) and
delegates literally everything else to grasp_executor.GraspExecutor (see
3.x). The actual grasp state machine, retries, and safety gates live
there, not here.

--------------------------------------------------------------------------
2.5  navigation_node.py   (scripts/navigation_node.py)
--------------------------------------------------------------------------
Role: THE ONLY cmd_vel publisher. All base motion goes through this node.

Services it serves (/locobot/navigation/...):
    ~drive_relative   (DriveRelative)   turn in place (closed-loop on
                                        odometry yaw), then drive straight
                                        (timed, open-loop). Independently
                                        testable: `rosservice call
                                        /locobot/navigation/drive_relative
                                        "{turn: 0.5236}"`.
    ~approach_target  (ApproachTarget)  put the base at a given standoff
                                        distance in front of a named
                                        target, in one of 3 modes:
                                        COARSE (long approach), FINE
                                        (single-shot measure -> move ->
                                        verify-once -> decide), or
                                        CORRECT (one bounded nudge, used
                                        before retrying a failed
                                        pre-grasp).

It measures the target through world_model's own services (get_target /
get_scene) — it has no perception of its own — and moves the base through
base_controller.BaseController. The actual approach POLICY (when to turn,
when to drive, when to give up) lives in the pure module approach.py (see
3.x); this file just wires that policy to the real robot interfaces.

--------------------------------------------------------------------------
2.6  vlm_agent_node.py   (scripts/vlm_agent_node.py)
--------------------------------------------------------------------------
Role: the thin VLM planning layer. Full explanation of exactly how this
works is in PART 5 below (the user specifically asked for it). In one
line: it runs an agentic tool-use loop against a local Ollama model
(qwen3-vl:2b-instruct by default), giving it exactly two tools
(get_object, navigate_to), each of which is nothing but a ROS service
call into TaskOrchestrator. This node knows NOTHING about perception,
geometry, or motion — it is pure "which of my two buttons do I press
next, and am I done".

--------------------------------------------------------------------------
2.7  set_camera_angle.py   (scripts/set_camera_angle.py)
--------------------------------------------------------------------------
Role: trivial, one-shot utility. Waits a few seconds (so the pan/tilt
controllers are definitely up), publishes one latched Float64 command to
each of /locobot/pan_controller/command and /locobot/tilt_controller/
command to point the camera down at the table, sleeps 1 second so the
latched message definitely propagates, and exits. Not a long-running
node — it has no rospy.spin() at all.


================================================================================
PART 3 — THE PURE LOGIC MODULES (imported, never launched)
================================================================================

These files contain no ROS node of their own; they're imported by one or
more of the 7 nodes above. Most of them are explicitly written to be
"pure" (no rospy import at all) specifically so they can be unit-tested
without ROS or Gazebo running — this is why test/ can run in ~1 second
with `python3 test/test_grasp_planner.py`.

Grouped by which part of the pipeline they belong to:

--- Perception / world-model support -----------------------------------

world_model.py (scripts/world_model.py)
    The actual fused "what is where" state machine. One instance lives
    inside WorldModelNode. Owns: the running target lock + recent-position
    history (for the median filter), a per-class size-calibration buffer
    (only trusts size measurements from frames taken >= 0.47 m away —
    measured that closer frames are systematically worse, both the raw
    bbox estimate and a naive centre-derived alternative), and a
    TableEstimate. Rejects implausible detections before locking onto
    them (sane_target: catches things like a detection at z=-0.012m
    "floating" through the floor). Caps the footprint of any UNcatalogued,
    non-surface object to 0.15 m — this exists because YOLO3D fills in
    a per-class SIZE PRIOR for classes it can't actually measure (e.g. a
    generic "person" prior of 0.6x0.6m), and a small mislabelled object
    was once turned into a phantom 0.64m obstacle that blocked the arm's
    own ready pose. obstacles() excludes every catalogued SURFACE label
    (catalog.surface_labels(), i.e. the table) from the generic-obstacle
    list, same exclusion already applied to the target's own label — found
    missing live (2026-09-29, commit 12bd7ac): without it, a noisy "dining
    table" detection became a duplicate, uncapped (surface detections are
    deliberately not size-capped), wrongly-placed phantom obstacle sitting
    in the approach corridor, blocking pre-grasp entirely.

world_table.py (scripts/world_table.py)
    Just the table's estimated geometry (surface height, near/far edge,
    width/depth), built from "dining table" detections. Deliberately
    conservative: only accepts a measured surface height if it's within
    10 cm of the known world-file constant (an object sitting ON the
    table can pull the bbox centre-derived estimate up).

zones.py (scripts/zones.py)
    Pure geometry: turn one raw detection dict into an enriched "parsed
    object" (distance, grasp axis, whether it fits the gripper), find
    which objects block the approach corridor, classify the current
    "zone" (grasp_ready / drive_forward / rotate_needed / path_blocked /
    target_not_found), and build the one-line English summary string the
    VLM reads. Also holds several genuinely global physical constants
    (ARM_REACH_M, TABLE_SURFACE_Z, GRIPPER_W_M, ...) that other files
    import from here rather than redefining.

resolver.py (scripts/resolver.py)
    Answers exactly one question, in exactly one place: "is THIS
    detection the object the user asked for?". Reads config/objects.yaml
    (via ObjectCatalog) and scores each candidate detection by confidence
    x plausibility (does its measured size roughly match the catalogue
    entry?), so that when two different physical objects share the same
    (wrong) YOLO label, the one whose size actually matches wins instead
    of racing on whichever frame arrived first.

target_state.py (scripts/target_state.py)
    One function, measured_position(): given everything the world model
    knows about the target (a TargetState message), decide which single
    (x, y) to trust — the median of recent detections (best, if there are
    enough), else the last accepted lock, else a map-frame reprojection.

target_odom_cache.py (scripts/target_odom_cache.py)
    Holds the target's position in the ODOM frame (continuous wheel
    odometry — never jumps, unlike the map frame which rtabmap corrects
    discontinuously). measure() caches a fresh median while the robot is
    stationary; set() caches an explicit, more-precise point (used to
    re-prime the cache with the depth planner's own real-geometry
    measurement, since raw YOLO3D positions have a documented
    range-dependent radial bias); reproject() answers "where is that
    cached point NOW, in the current base frame" — valid mid-motion and
    when the camera can't see the object at all (e.g. the arm is in the
    way at grasp height). This is what lets the grasp's safety checks
    work even though the gripper physically blocks the camera during the
    final approach.

world_bev.py (scripts/world_bev.py)
    Pure OpenCV/numpy: renders the top-down "bird's-eye view" debug/VLM-
    feedback image (robot, target, obstacles, gripper corridor, grasp
    points, table footprint, arm-reach circle). No ROS.

conversions.py (scripts/conversions.py)
    The ONE place that knows both the pure-Python dict/list shapes the
    geometry code uses (e.g. dims_hwl = [Height, Width, Length]) and the
    actual locobot_prog ROS message shapes (which use named axes, x =
    depth/y = width/z = height). Every message <-> dict conversion in the
    whole project goes through here, so that index-0-is-height convention
    never leaks into ROS-facing code.

locobot_geometry.py (scripts/locobot_geometry.py)
    Historically a much bigger file (scene-parsing, zone classification,
    bird's-eye rendering) that has since been almost entirely superseded
    by zones.py / world_table.py / world_bev.py and deleted as dead code.
    What's LEFT is exactly one function, estimate_grasp_orientation():
    fits a minimum-area rectangle to the object's depth-masked (or
    Canny-edge, if no depth) silhouette to estimate its yaw, short-
    circuiting to "0 = symmetric, no meaningful yaw" for round objects,
    and resolving the classic 180-degree ambiguity of a fitted rectangle
    using the viewing-ray angle. Used only by detection_shim.py.
    Takes a `symmetric` override (bool or None), fed from the object
    catalogue's `round` field via detection_shim.py, instead of inferring
    "round" purely from the footprint being square — added 2026-10-05
    after that inference wrongly zeroed tea_box's real yaw (45x45mm
    footprint, same ratio as a ball's, but 4 flat faces, not round).
    symmetric=None (uncatalogued) keeps the old dims-ratio-guess behaviour
    unchanged.

rotations.py (scripts/rotations.py)
    A small, dependency-free (no `tf` import) reimplementation of the
    handful of quaternion functions this project actually needs
    (quaternion_from_euler, quaternion_matrix, world_to_body,
    yaw_from_quaternion). Exists so the geometry layer can be imported
    and unit-tested on a machine with no ROS `tf` package installed.
    world_to_body is used for ground-truth comparisons and correctly
    accounts for the robot's full 3-D orientation (it rests pitched ~2
    degrees nose-down on its front caster — a yaw-only transform was
    found to put a ground-truth point ~12 mm off).

ground_truth.py (scripts/ground_truth.py)
    A thin wrapper around Gazebo's /gazebo/get_model_state service, used
    ONLY for diagnostics (see arm_diagnostics.py) — comparing the
    odometry-based estimate the real safety gates use against Gazebo's
    privileged "true" object pose, to measure how accurate the
    hardware-portable estimate actually is. Every method degrades to
    None when Gazebo isn't there (a real robot, or a sim without the
    service) — nothing in the actual grasp logic is allowed to depend on
    it, specifically so the whole pipeline stays meaningful on real
    hardware.

--- Navigation support ---------------------------------------------------

base_controller.py (scripts/base_controller.py)
    Owns the actual cmd_vel publisher and the two primitive motions:
    rotate_to_yaw() (closed-loop P-controller on odometry yaw, gain 2.0,
    stops within 0.15 degrees, falls back to a timed turn if TF is
    briefly unavailable) and drive() (timed, open-loop straight-line
    drive — an odometry-closed-loop version was tried and reverted after
    it failed on a real run).

approach.py (scripts/approach.py)
    Pure policy (no rospy import at all): given a small "robot" interface
    (measure/rotate/drive/face/...), decides how to get the base to a
    given standoff distance in front of a target. Three entry points:
    coarse() (long-distance approach, kept a margin from the table edge),
    fine() (the single-shot GO -> VERIFY-once -> DECIDE positioning used
    for the actual grasp approach — deliberately NOT an iterative
    convergence loop, because an earlier iterative version re-rotated
    forever chasing sub-noise bearing jitter), and correct() (one bounded
    nudge before retrying a failed pre-grasp).

--- Grasp geometry / execution --------------------------------------------

grasp_geometry.py (scripts/grasp_geometry.py, 490+ lines)
    The formula-based geometry toolbox AND the BASELINE grasp plan (used
    whenever the real depth-based planner declines or isn't available).
    Key pieces: grasp_height_above_table() (a blind formula, floor/
    ceiling-clamped, for when there's no real measurement to use instead),
    is_tapered()/gripper_close_target() (the older tapered-vs-uniform
    binary close-target rule — STILL the one actually used by
    baseline_plan(), since that path has no real per-band width
    measurement to squeeze against), pregrasp_pose()/grasp_pose() (the
    standoff-and-approach geometry), pregrasp_verdict()/contact_verdict()
    (the two hard-coded but live-rosparam-tunable pass/fail gates used by
    grasp_executor.py), descent_aim()/descent_height() (the small
    re-aiming logic that follows the base's own tilt/creep), and
    table_box()/target_box()/obstacle_boxes() (the MoveIt collision boxes
    the whole scene is built from).

    grasp_pose()/baseline_plan() take an `orientation` parameter (2026-
    10-05): the object's measured yaw, radians, None for a round object or
    when never measured. Without it the gripper's yaw was always
    atan2(y, x) — "face the object's centre", correct for a round object
    but physically uncorrelated with a box's real rotation otherwise. A
    few degrees of mismatch is enough for the ~3mm per-side jaw clearance
    to catch a corner instead of a face — confirmed live via ground-truth
    pose trace: a corner-caught tea_box pick toppled it 45-67 degrees in
    roll/pitch while being lifted. A near-square footprint has an EXTRA
    wrinkle on top of that: cv2.minAreaRect (inside
    locobot_geometry.estimate_grasp_orientation) can return any of 4
    equally-valid 90-degree-apart face alignments, and backing the
    standoff off along the "wrong" one sends it ~90-100mm sideways instead
    of in front of the object, breaking pre-grasp reachability.
    _nearest_square_equivalent(yaw, bearing) snaps to whichever
    90-degree-equivalent representation stays closest to the robot's own
    bearing — found necessary only AFTER the first version of the
    orientation fix shipped and broke reachability in 2/2 live trials.

grasp_planner.py (scripts/grasp_planner.py, 301 lines)
    The REAL, depth-measurement-based grasp planner. Full explanation in
    PART 4.

footprint.py (scripts/footprint.py, 127 lines)
    The depth-image geometry grasp_planner.py runs on: back-project depth
    pixels to 3-D (backproject), move them into base_link (transform),
    cut to just the target object (object_points, using a centre + radius
    cut), slice into horizontal bands and measure each one's real lateral
    width (bands), and — the newest addition — measure the REAL support-
    surface height from the same depth frame (table_height), rather than
    trusting a config constant. Pure numpy + OpenCV, no ROS.

reach.py (scripts/reach.py)
    Inverse-reachability: sweeps a small grid of candidate standoff
    distances and, for each, IK-solves several points along the whole
    planned approach, scoring by how far every joint stays from ITS OWN
    limit (a "joint margin"), preferring a standoff whose neighbours are
    ALSO comfortable (a plateau, so a little base positioning error still
    lands somewhere good). MoveIt can't plan the (non-holonomic, drifting)
    base itself, so this is how the system still picks a sensible
    standoff distance for the base to drive to.

collision_scene.py (scripts/collision_scene.py)
    A small wrapper around moveit_commander.PlanningSceneInterface:
    add/replace/remove the table+neighbour obstacle boxes, add/remove the
    target-as-obstacle box (for the pre-grasp phase), attach/detach the
    grasped object (so the retreat plans around its extra bulk), and
    clear() (tear everything down at the end of a grasp attempt, success
    or failure).

grasp_executor.py (scripts/grasp_executor.py, 730+ lines)
    The actual two-phase grasp STATE MACHINE — everything arm_node.py's
    services delegate to. pregrasp() and grasp() are its two public
    methods (mirroring ExecutePregrasp/ExecuteGrasp exactly), plus
    place(). Owns every retry rule described in the session's earlier
    discussion: the pre-grasp offset-closing retry, the wrist-singularity
    detection + re-seat-and-retake retry on the final leg, the contact-
    verification gate before closing the jaws, and the "did we actually
    hold something" physical-evidence check (_outcome) that can override
    a reported planning failure if the gripper width says otherwise.

    TWO fixes added 2026-10-05, both found by live-testing the orientation
    fix above:

    1. pregrasp() now sets the waist angle (the only joint
       GRASP_READY_POSE leaves free, so it alone sets the end-effector's
       yaw for the WHOLE approach and descent, via _wp_for carrying that
       same orientation through unchanged) from the plan's own
       grasp_orientation, instead of a freshly-computed atan2(y, x). This
       had been the real gap behind the corner-catch bug even after
       grasp_pose()'s orientation fix shipped: that fix's measured yaw
       only ever reached pregrasp_pose()'s STANDOFF-POSITION calculation
       (which direction to back away from the grasp point), never the
       commanded gripper rotation — so a box resting at a genuine angle to
       the robot's bearing was still being closed on bearing-aligned, not
       face-aligned, jaws. Verified in isolation via a direct
       arm/execute_pregrasp call with grasp_point dead ahead (bearing=0)
       and grasp_orientation yaw=30 degrees: logged "Waist to target:
       0.524 rad (30.0 degrees)" (the old code would log 0.0), verified at
       4.6mm / 1.3 degrees of execution error.

    2. _do_descent() gates on a gripper STALL: if the fingers move less
       than MIN_CLOSE_TRAVEL_MM (3mm) despite a real close command, the
       attempt is reported as a FAILURE (release past grasp_fix's
       release_tolerance, retreat) instead of a false success. Root cause:
       gazebo_grasp_fix (see the GazeboGraspFix / urdf/grasp_fix.urdf.xacro
       note under "Grasp geometry / execution" below) welds an object to
       the palm on ANY two roughly-opposing contact points sustained for
       just 100ms, with zero regard for commanded finger position — the
       open (56mm) jaws can graze a near-square object's corner during the
       straight-in descent and weld prematurely, before the deliberate
       squeeze ever runs, freezing whatever disturbance that graze caused
       (confirmed caught live: "Gripper stalled 0.1mm from fully open...
       Releasing and retreating").

GazeboGraspFix — why a squeeze command can move the fingers almost nothing,
and the object still doesn't fall (~/th_ws/src/gazebo-pkgs/gazebo_grasp_
plugin/src/GazeboGraspFix.cpp — NOT part of this repo, a separate catkin
package this workspace also builds)
    Read directly from its source during this session's stall-gate
    investigation. CheckGrip() (OnUpdate, ~20Hz per urdf/grasp_fix.urdf.
    xacro's own <update_rate>) scans every current contact point on the
    held object for ANY PAIR whose force vectors are more than
    forces_angle_tolerance (120 degrees) apart, with the weaker at least
    lengthRatio (0.3) of the stronger — i.e. "is anything touching the
    object from two roughly opposing directions", not "are the two
    fingertip pads cleanly squeezing it". With grip_count_threshold=1 at
    20Hz, TWO qualifying ticks — 100ms — permanently welds the object to
    the palm link, in whatever relative pose it's in at that instant,
    regardless of commanded finger position. The jaws travel OPEN (56mm)
    around a ~50mm object during the straight-in descent leg, BEFORE the
    deliberate squeeze command ever runs (grasp_executor.py's own
    docstring already documents one earlier, grosser incident of exactly
    this: an object brushed with no close command at all, dragged 254mm
    on retreat); a near-square object's corner can graze a pad during that
    approach and weld prematurely, freezing whatever nudge that graze
    caused — explaining why a subsequent close command can then move the
    fingers almost nothing (they're now moving against an object already
    rigidly fixed to the palm, not closing on open air) while the object
    stays held the whole cycle (a weld, unlike finger friction, needs no
    ongoing squeeze force). This project also carries a LOCAL PATCH to
    this external package (see git -C ~/th_ws/src/gazebo-pkgs diff and
    urdf/grasp_fix.urdf.xacro's own release_tolerance comment): upstream's
    detach check compares only the LENGTH of the contact-to-object-origin
    vector, which failed to release a tall bottle (origin far below a neck
    grip, so opening the jaws barely changed that length); the patched
    version uses a displacement metric instead.

arm_actuators.py (scripts/arm_actuators.py)
    The lowest layer: ArmActuator (raw joint-space commands straight to
    the arm controller's command TOPIC, bypassing MoveIt's execute()
    action interface — deliberately, because that interface aborts the
    whole trajectory the instant the deliberately low-gain forearm_roll
    joint lags past its tolerance) and Gripper (open/close commands +
    reading the current finger position off /joint_states). Also holds
    ArmActuator.hold() — the "settle-hold" pattern: re-command the arm's
    own just-measured joint values so the (low-gain, damped-on-purpose)
    effort controllers stop hunting, with a sanity check against the last
    COMMANDED pose so a garbage joint-state read (all zeros was observed
    live) can't be blindly re-sent through the target.

arm_diagnostics.py (scripts/arm_diagnostics.py)
    Measurement-only (never changes behaviour): reads the actual finger-
    link TF positions and the actual end-effector pose to compute real,
    ground-truth-comparable numbers — pregrasp() (commanded vs. achieved
    pose, position + orientation error) and contact() (is the object
    really straddled between the open jaws, measured two ways: from the
    caller-supplied odometry position, which is what the safety gate
    actually uses, and — only when ~diag_object_model is set — from
    Gazebo's own ground truth, purely for accuracy comparison, never for
    gating).

PART 4 — HOW THE DEPTH-BASED GRASP PLANNER ACTUALLY WORKS
================================================================================

This is the single most important piece of "real" (non-VLM, non-formula)
intelligence in the project, so it's worth a dedicated section.

The question it answers: "given a real depth-camera image of this object,
exactly where should the jaws close, how wide should they open, and how
far should they squeeze?" — as opposed to the older baseline_plan(),
which only ever knew the object's bounding-box centre and a rough
formula for height.

Pipeline, end to end (grasp_planner.plan_from_points + footprint.py):

  1. TABLE HEIGHT — footprint.table_height(). Looks at a strip of the
     SAME depth frame, around and below the target's bounding box, cut
     to exclude the target itself. Histograms the points near the
     assumed table height and takes the LOWEST well-populated bin (so an
     object standing ON the table can't be mistaken for the table
     itself). This replaced a hardcoded world-file constant that was
     measured to be off by ~23-24 mm from what the camera actually sees
     — an error every downstream "height above the table" calculation
     had silently inherited.

  2. POINT CLOUD — footprint.backproject() turns every depth pixel
     inside the (slightly padded) detection box into a 3-D point in the
     camera's optical frame; footprint.transform() moves it into
     base_link using the camera->base TF looked up AT THE FRAME'S OWN
     TIMESTAMP (not "now" — detections lag their source image by a
     measurable amount); footprint.object_points() keeps only the points
     above the (now correctly measured) table and within a radius of the
     object's estimated centre (so a neighbouring object sharing the
     same detection box gets excluded).

  3. HEIGHT BANDS — footprint.bands() slices the remaining points into
     5 mm horizontal bands and measures each band's real lateral extent
     (the width across the direction the jaws would close) directly from
     the points — no formula, no class-size guess.

  4. THE HIDDEN BACK — a single camera only ever sees the FRONT of the
     object. Each band is completed by reflecting it through its own
     estimated centre (exact for anything centrally symmetric — bottles,
     cans, most graspable objects).

  5. CLOSING AXIS + CONTACT POINTS — for each band, grasp_planner.py
     rotates a candidate closing axis (usually straight across the
     approach direction, optionally deviating a little) and uses
     OpenCV's convexHull + a rotating "width function" w(theta) (the
     distance between the two support lines of the hull at that angle)
     to find exactly where the two jaw faces would land, how wide that
     is, and how far the object would TURN in the jaws before seating
     flat (quality = cos(turn); 0 degrees for anything round or a box hit
     square-on).

  6. SCORING (_band_score) — every band across the object's WHOLE
     physically-reachable height (not a narrow window around a guessed
     "expected" height — that used to be a real bug: it silently made a
     bottle's genuinely-better neck unreachable) is scored by: how little
     it will turn in the jaws, how much clearance the OPEN jaws have
     across the object's FULL vertical pad height (not just the one
     band — a jaw pad is a ~29mm-tall vertical strip, and a band whose
     own width fits fine can still have the pad's edge touching a much
     wider part just above or below it), a small tie-break preference for
     being near the old formula's guessed height, and a small penalty for
     deviating from the default closing axis.

  7. THE ACTUAL SQUEEZE — the winning band's grasp point becomes the
     commanded height; the gripper's CLOSE target is computed as "the
     widest the object gets anywhere within the pad's own height" minus a
     small deliberate SQUEEZE (currently 4 mm per finger — tuned down
     from 6 mm after a live test showed 6 mm was enough interference on a
     tapered surface to tip the object over and drag it 38 mm during the
     close).

  8. FALLBACK — if any step fails (not enough points, no band fits the
     jaw span at all, too short for a side grasp), plan_from_points()
     returns None with a plain-English reason, and
     TaskOrchestrator._choose_plan() silently falls back to
     grasp_geometry.baseline_plan() — the object's pick is never worse
     than it would have been without this planner at all, it just may be
     less well-centred.

All of this is exercised by 23 offline unit tests
(test/test_grasp_planner.py) against SYNTHETIC, ray-cast depth images
with a mathematically known right answer (test/synthetic_depth.py) — no
ROS or Gazebo needed to test any of it.

PART 5 — THE VLM: EXACTLY WHAT HAPPENS WHEN IT'S CALLED
================================================================================

Model: qwen3-vl:2b-instruct by default (a small, LOCAL vision-language
model), served by Ollama running on the same machine — NOT a cloud API
call. Configurable via the vlm_model launch argument. The node talks to
it through the `ollama` Python package's chat() function, which hits
Ollama's local HTTP server.

What the VLM is given, every time it's asked to think:
  - A SYSTEM PROMPT (hardcoded in vlm_agent_node.py's SYSTEM_PROMPT
    constant) explaining it's an autonomous LoCoBot manipulation agent,
    describing its two tools, and giving it an explicit workflow: call
    get_object, check whether gripper_width_m exceeds the "holding
    something" threshold (0.015 m — a constant that is DELIBERATELY
    computed from the same GRIP_HELD_MIN_WIDTH the real code uses, so the
    prompt's stated threshold can never silently drift out of sync with
    what the code actually checks), retry up to 3 times total if it
    failed, then report the outcome.
  - The full running conversation history (every message, every tool
    call, every tool result, every feedback image, all kept in one
    growing `messages` list for the whole episode).
  - EXACTLY TWO TOOLS, defined as ordinary Python methods on the node:

      get_object(target_name)
          Calls TaskOrchestrator's /locobot/task/get_object service.
          This is the ENTIRE pick: observe the scene, navigate to it,
          pick it up, put it back down. Returns a dict (success,
          gripper_width_m, zone, scene_summary, phase, description,
          visible_objects) which gets serialized to JSON and handed back
          to the model as a "tool" role message.

      navigate_to(target_name)
          Calls /locobot/task/navigate_to. Drives to the object and stops
          in front of it, without grasping.

    The `ollama` client auto-generates each tool's JSON schema from the
    Python function's own type hints and docstring — this is why each
    tool method's docstring is written in the Args:/Returns: style: it
    is LITERALLY what the model reads to decide how to call it, not just
    a comment for humans.

  - After every tool call, feedback IMAGES are appended as a new "user"
    role message (with no text) so the model can visually check what
    happened: the freshly-rendered bird's-eye view (if the task produced
    one) and/or the live camera frame (JPEG, resized to 320x240, quality
    75, base64-encoded) — this is how the VLM "sees" whether the gripper
    is holding the object afterward, not just reading a boolean.

The loop itself (VlmAgentNode.run()):
  1. Wait for the first camera frame (up to 15 s), then send the system
     prompt + a user message ("Pick up the <target_object>.") with the
     current camera frame attached.
  2. For up to max_steps rounds (default 5, from vision_nodes.launch):
       a. Call ollama_chat(model=..., messages=..., tools=[get_object,
          navigate_to], stream=False, think=False) — a single, complete
          (non-streamed) response, with the model's internal "thinking"
          mode explicitly turned off. (There's a fallback for older
          `ollama` client versions that don't accept the `think` kwarg
          at all.)
       b. If the model replied with NO tool call, nudge it once
          ("Call get_object now.") and loop again — unless this was
          already the last allowed step, in which case just log its
          final text and stop.
       c. Otherwise, execute every tool call the model asked for, append
          each JSON result as a "tool" message, and append any feedback
          images as a follow-up "user" message.
  3. Between any two tool calls, _pace() enforces a minimum interval
     (grasp_min_interval_s, default 5.0 s) — this exists so the physical
     world (and the camera) has time to actually settle between actions,
     not to slow the model down for its own sake.

What the VLM DOES NOT do: it never sees raw sensor data beyond the two
images described above, never touches geometry, never decides HOW to
grasp (height, width, squeeze, standoff distance — all of that is fully
deterministic code in world_model_node/grasp_executor). Its only real
decision is WHEN to call which of its two tools and when to declare the
episode done. This is intentional: the thesis's manipulation reliability
work lives entirely in the classical pipeline; the VLM is a thin,
swappable planning layer on top of it (the file's own docstring notes
the interface — get_object/navigate_to as plain service calls — was
deliberately kept generic enough that a different agent, or even a human
typing rosservice calls by hand, drives the exact same pipeline).

Running WITHOUT the VLM (used constantly during this project's
development/debugging, because Ollama alone needs ~2.7 GB RAM): launch
with use_vlm_agent:=false and drive the pipeline directly —
    rosservice call /locobot/task/get_object "target_name: 'bottle'"
does exactly what the VLM's get_object tool call would have done.

PART 6 — SERVICES AND MESSAGES: HOW THEY'RE DEFINED, BUILT, AND LOADED
================================================================================

6.1  Where they're defined
---------------------------
  srv/*.srv   — 14 files, one per ROS SERVICE type (request fields, a
                "---" separator line, response fields).
  msg/*.msg   — 7 files, one per ROS MESSAGE type (used either as a field
                inside a .srv, or standalone, e.g. published on a topic).

This project does NOT use plain topics with generic message types for
anything action-like — every "do something and tell me what happened" is
a typed .srv, by explicit, repeated design choice (the CMakeLists.txt
comment literally says this replaces an older "JSON-blob-over-topic
dispatch" design from an earlier, retired version of the project).

6.2  How catkin turns them into usable Python code
----------------------------------------------------
  1. package.xml declares a build_depend + build_export_depend +
     exec_depend on message_generation / message_runtime — the catkin
     machinery that does this work.
  2. CMakeLists.txt lists every file:
        add_message_files(FILES GraspPlan.msg CollisionBox.msg ...)
        add_service_files(FILES SetArmPose.srv SetGripper.srv ...)
        generate_messages(DEPENDENCIES std_msgs geometry_msgs sensor_msgs)
     generate_messages() is what actually invokes the code generator.
  3. Running `catkin_make` (from the workspace root, ~/th_ws) processes
     every listed .srv/.msg file and writes real Python classes into
        ~/th_ws/devel/lib/python3/dist-packages/locobot_prog/msg/_X.py
        ~/th_ws/devel/lib/python3/dist-packages/locobot_prog/srv/_X.py
     (one file per type, each defining e.g. GraspPlan, GraspPlanRequest
     is not a thing for messages but IS generated for services: every
     Foo.srv produces FooRequest and FooResponse Python classes plus a
     combined Foo "service class" object used to register/call the
     service).
  4. Sourcing ~/th_ws/devel/setup.bash puts that generated
     dist-packages directory on PYTHONPATH, which is why every script in
     this project can do:
        from locobot_prog.msg import GraspPlan, CollisionBox, ...
        from locobot_prog.srv import SetArmPose, SetArmPoseResponse, ...
     exactly like importing any other installed Python package — nothing
     ROS-specific about the import syntax itself, all the "ROS-ness" was
     already baked in by the code generator.
  5. IMPORTANT PRACTICAL CONSEQUENCE: any time a .srv or .msg FILE is
     edited (a field added/removed/renamed), the workspace must be
     rebuilt (`catkin_make`, or `catkin_make --pkg locobot_prog` to only
     rebuild this package) before the Python change is visible anywhere
     — editing the .srv text alone does nothing until the generator has
     re-run. This tripped up this exact session once: after editing
     PlanGrasp.srv to add a table_z response field, the field didn't
     exist in the generated Python class (and a live sim couldn't even
     start with the right ROS_PACKAGE_PATH) until catkin_make was re-run.

6.3  How a service is "loaded" at runtime (declared vs. called)
-------------------------------------------------------------------
A .srv type being generated doesn't create a running service — two more
things have to happen, both ordinary rospy calls, both visible directly
in the node's __init__:

  SERVER side (one line per service, inside the node that owns the
  behaviour):
        rospy.Service("~execute_grasp", ExecuteGrasp, self._execute_grasp)
  The "~" prefix means "relative to this node's own private namespace" —
  e.g. inside arm_node.py (which rospy.init_node("arm")s under the
  "locobot" namespace from its launch <node> tag), this actually
  registers /locobot/arm/execute_grasp. A few services (world_model's
  TaskOrchestrator half) are registered with an EXPLICIT absolute path
  instead (f"/{ns}/task/get_object") specifically so external callers
  (the VLM agent) can find them at one fixed, memorable address
  regardless of which node happens to host that class.

  CLIENT side (one line per service, inside whatever node wants to CALL
  it):
        self._get_object = rospy.ServiceProxy(f"/{ns}/task/get_object",
                                              GetObject)
  ...often preceded by rospy.wait_for_service(..., timeout=...) so the
  node doesn't crash if it starts up before its dependency is ready — it
  just waits (and logs an error if it times out).

  Every single one of this project's 14 services was checked this
  session and has EXACTLY one server and at least one real caller — see
  PART 7 for the two that are served but not called by any automated
  code path (they're deliberate manual/debug entry points, not dead
  code).

6.4  Every service and message in the project, and who owns each
----------------------------------------------------------------
  Served by arm_node:
    SetArmPose, SetGripper, GetGripperState, ExecutePregrasp,
    ExecuteGrasp, ExecutePlace
  Served by navigation_node:
    DriveRelative, ApproachTarget
  Served by world_model_node (WorldModelNode half):
    GetScene, GetTarget, TargetMemory, PlanGrasp
  Served by world_model_node (TaskOrchestrator half, absolute paths):
    GetObject, NavigateTo

  Messages (used as .srv fields and/or standalone on topics):
    GraspPlan       — the full description of one grasp (see 3.x above)
    CollisionBox    — one axis-aligned MoveIt collision box
    WorldObject     — one object as the world model reports it
    TableModel      — the table's estimated geometry
    TargetState     — every source of "where is the target" the world
                      model has, for a caller to pick from
    Detection3D     — one raw camera detection, in base_link
    DetectionArray  — a whole frame's worth of Detection3D (the shim's
                      output, world_model's input)

6.5  Non-service communication (plain topics), for completeness
--------------------------------------------------------------------
Not everything is a service — genuinely continuous/streaming data uses
ordinary topics instead: camera color/depth images and camera_info
(published by Gazebo's camera plugin), /locobot/locobot_prog/detections_3d
(String/JSON, yolo_detection_node -> detection_shim),
/locobot/locobot_prog/detections (DetectionArray, detection_shim ->
world_model), /locobot/cmd_vel (Twist, navigation_node's only output),
/locobot/joint_states (from Gazebo's controllers, read by arm_actuators.py
and by world_model_node for the odometry cache's freshness), /locobot/scan
(LaserScan, read by navigation_node for the "front blocked" veto), and the
pan/tilt controller command topics (Float64, set once by
set_camera_angle.py).

      earlier Claude Code sessions), sitting in what would normally be a
      C++ header install directory (this package has no C++ library, so
      that directory is otherwise unused). Not referenced by any build
      rule or launch file. Genuinely just historical design
      documentation — worth KEEPING for the thesis write-up (they
      document the reasoning behind real fixes), but they are not part
      of the running system in any way.

7.2  Deliberately "unused by automated code, but not dead" — debug/manual
       entry points
-------------------------------------------------------------------------
  GetGripperState  (arm_node's ~get_gripper_state service)
  DriveRelative    (navigation_node's ~drive_relative service)
      Both are real, correctly-implemented, served-and-working services
      — but no automated code path in the current pipeline calls either
      of them as a CLIENT. Both nodes' own docstrings show them being
      used via a manual `rosservice call ...` for independent testing.
      This matches a deliberate, stated pattern in this project ("this
      node is Independently runnable and testable on its own") — they
      are debug/verification seams, not orphaned code, and removing them
      would remove real testing/inspection capability.

7.3  Things that LOOK like duplication but aren't
------------------------------------------------------
  grasp_geometry.gripper_close_target() / is_tapered()  vs.
  grasp_planner.py's own contact-width-based squeeze logic
      Both compute a gripper close target, which looks redundant at a
      glance. They are NOT: grasp_geometry's version is used ONLY by
      baseline_plan() — the fallback path that has nothing but a
      bounding-box width to work with, so the older tapered/uniform
      binary rule is the only thing it CAN do. grasp_planner.py's
      version is used only by the real, depth-measured plan, which knows
      the object's actual per-band width profile and can squeeze a fixed
      small amount past a real measured contact point instead. Verified
      by checking every call site this session — no accidental
      duplication, no leftover code from the switch to the new squeeze
      logic.

  test/ not wired into `catkin_make run_tests`
      CMakeLists.txt has `# catkin_add_nosetests(test)` commented out —
      tests are NOT run automatically by the catkin build. This looks
      like an oversight but is explained by the test files' own
      structure: each test_*.py file has its own `if __name__ ==
      "__main__":` runner and is meant to be run directly
      (`python3 test/test_grasp_planner.py`), not through nose/pytest
      discovery. This is a real, working test suite (~64 tests across 7
      files — see PART 9) — just invoked by hand rather than through the
      catkin test target.

7.4  Everything else: genuinely used
----------------------------------------
  Every other .py file in scripts/ is imported by at least one of the 7
  launched nodes (verified by building the full import graph, not just
  spot-checking); every .srv and .msg has exactly one server and at
  least one real caller; rviz/locobot_moveit.rviz is wired up (behind
  use_rviz + use_moveit_rviz, both off by default); config/
  arm_gains_override.yaml and config/objects.yaml are both loaded by
  locobot.launch / consumed by resolver.py+world_model.py respectively.
  There is no other dead code in this package as of this audit.

PART 8 — LAUNCH FILES, WORLDS, AND CONFIG — THE ACTUAL ENTRY POINTS
================================================================================

launch/locobot.launch
    The real base launch file. Spawns Gazebo with the given world_name
    (default: worlds/locobot_two_room_env.world), the LoCoBot robot
    description (with this project's own external_urdf_loc =
    urdf/grasp_fix.urdf.xacro merged in — this is what adds the
    GazeboGraspFix plugin and the finger-pad friction/stiffness
    overrides), MoveIt (interbotix_xslocobot_moveit), and, right at the
    end, loads config/arm_gains_override.yaml LAST (so it wins over the
    vendor PID gains uploaded earlier by the included MoveIt/Gazebo
    launch files — roslaunch uploads ALL params before starting any
    node, so load order in the XML is what decides which value survives).
    Conditionally includes launch/vision_nodes.launch when
    use_vision_nodes:=true (default false — plain `roslaunch
    locobot_prog locobot.launch` on its own gives you an empty
    perception-free simulation, useful for pure arm/nav testing).

launch/vision_nodes.launch
    Spawns the 6 non-Gazebo nodes: yolo_detection_node, detection_shim,
    world_model_node, arm_node, navigation_node, and (if
    use_vlm_agent:=true, the default) vlm_agent_node, plus
    set_camera_angle.py. This is the file to read for the exact
    parameters each node starts with (YOLO model path, confidence
    threshold, target classes, VLM model name, max agent steps, etc.).

launch/locobot_table_arm.launch
    A convenience wrapper around locobot.launch, redundant with its
    defaults (see PART 7.1) — still points at the two-room world.

launch/locobot_table.launch
    Launches worlds/locobot_table.world instead of the default — the
    plain single-room pick-and-place world, for when the two-room
    environment isn't wanted.

worlds/locobot_two_room_env.world  (2026-10-06, renamed from
                                    locobot_table_arm.world)
    The CURRENT, live, DEFAULT scene — two rooms connected by an open
    doorway:
      Room A (x: -1.5..4.5, y: -3..3) — the original pick-and-place
        room. The table (now rotated 90 degrees so its long edge sits
        flush near the north wall, like a desk) still holds bottle
        (model://bottle_beer), tea_box, and can_coke; the 4th original
        object (a ball) was removed and replaced with a plain decorative
        cup (model://cup_blue, named "mug" — NOT in config/objects.yaml,
        not a grasp target). Also furnished with a sofa, two chairs, a
        floor lamp, two plants, a second file cabinet, and a trash bin —
        none of these are catalogued or obstacles to the grasp pipeline,
        purely cosmetic. A pavement floor tile and a window were added
        to the room's own walls.
      Room B (x: 4.5..10.5, y: -3..3) — a new office room: a desk with
        a monitor and chair, a bookshelf, a second sofa, a side table,
        a file cabinet, a plant, a window, and a wall picture — all
        placed via repeated live verification (several items' default
        mesh orientation did NOT match their intuitive "yaw=0" facing,
        caught only by looking at live camera captures from the actual
        running sim, not by reasoning about the SDF alone).
    Every wall/furniture piece is a separate top-level <model>/<include>
    in this flat world file — none of it is parented to the robot or to
    MoveIt's planning scene, so none of it is a collision obstacle to
    the grasp pipeline; it's set dressing, verified by confirming the
    table + its objects sit at their exact original ground-truth poses
    after every change in this room's long edit history.

worlds/locobot_table.world  (2026-10-06, new — a saved snapshot of the
                              original pre-two-room content, unchanged)
    The plain single-room scene this whole project was built and tuned
    against: just the 4 walls, the table at (0.70, 0.0), and all 4
    original objects (bottle, tea_box, can_coke, ball) at their original
    positions. No second room, no office furniture, no pavement/window.
    Use this (via launch/locobot_table.launch) for anything that should
    be clear of the two-room environment's extra scene complexity —
    e.g. collect_training_data.py's auto-labeling, which still expects
    a spawned "ball" model under that exact name.

config/objects.yaml
    The object catalogue consumed by resolver.py/world_model.py: for
    each graspable object, what names a user/VLM might call it, which
    (possibly wrong, but empirically measured) YOLO class labels it
    actually gets detected as, and its real size (used only to break
    ties between same-labelled candidates, never to override a real
    measurement). Adding a new graspable object to the simulation means
    adding an entry HERE, not editing any node's Python code. Also now
    (2026-10-05) a `round` field: true only for a genuinely circular
    cross-section (bottle, can_coke, the ball capsule) — deliberately NOT
    inferred from the footprint being square, since a square footprint
    (tea_box, 45x45mm) and a round one are different shapes; omitted/false
    is the default ("not round"). Feeds locobot_geometry.estimate_grasp_
    orientation's `symmetric` override via resolver.ObjectCatalog.is_round().

config/arm_gains_override.yaml
    The tuned PID gains for the Gazebo effort-based joint controllers —
    see this project's own detailed measurement log inside that file's
    comments for exactly why forearm_roll in particular is pinned back
    down to the true vendor value (p=5, i=0, d=0) after an earlier,
    silent vendor-file edit had pushed it to p=20 and caused visible
    arm oscillation.

urdf/grasp_fix.urdf.xacro
    Adds the libgazebo_grasp_fix.so plugin (rigidly welds the object to
    the gripper on first finger contact — a deliberate simulation crutch,
    since simulating stable friction-based grasping in Gazebo is
    notoriously unreliable) and high-friction/high-stiffness finger-pad
    material overrides, without touching any of the vendor interbotix
    URDF/xacro files. Its <forces_angle_tolerance>/<grip_count_threshold>/
    <update_rate> values are the plugin's actual weld-trigger config — see
    the GazeboGraspFix note under PART 3's "Grasp geometry / execution"
    for exactly how fast and loosely that trigger fires, and why.


================================================================================
PART 9 — TESTS
================================================================================

test/synthetic_depth.py
    Not a test itself — a small pure-numpy ray-casting renderer (camera
    matching the sim's real FOV) that produces synthetic depth images of
    simple scenes (cylinders, boxes, a table) with a mathematically KNOWN
    right answer, so grasp_planner.py can be tested against ground truth
    with no ROS/Gazebo at all.

test/test_grasp_planner.py  (largest suite)
    The depth-based planner end-to-end, against rendered synthetic
    scenes: correctly measuring a cylinder's width, resolving the hidden
    back of an object, choosing a roomier neck over a tighter body,
    respecting the jaw pad's full vertical span (not just one band),
    detecting a genuinely tapered surface, being robust to depth noise,
    correctly measuring the real table height from depth even when a
    constant "prior" is wrong, and computing the contact-width-based
    squeeze correctly (including on a continuously tapering surface).

test/test_arm_hold.py
    ArmActuator.hold()'s bad-joint-read guard: does it fall back to the
    last commanded pose on a garbage reading, does it correctly trust a
    plausible one, does publish_trajectory() correctly update
    last_target from a MoveIt-computed trajectory's final point.

test/test_descent_aim.py
    grasp_geometry.descent_aim()/descent_height(): the small live re-aim
    logic that follows base tilt/creep between planning and the actual
    descent — tolerance boundaries, refusal on an implausibly large
    shift, and a physical sanity check that the logged x-shift and
    z-shift numbers are consistent with one rigid rotation of the base.

test/test_world_model_sizes.py
    world_model.WorldModel._plausible_size()'s footprint cap: a
    catalogued or surface (table) label is never touched; an
    uncatalogued label with an implausible footprint gets capped.

test/test_grasp_orientation.py  (added 2026-10-05, 11 tests)
    The catalogue's is_round(), the symmetric override's three branches
    (True/False/None) on estimate_grasp_orientation, grasp_pose()/
    baseline_plan()'s orientation threading and reason string, the exact
    live corner-catch geometry from the topple reproduction, and the
    90-degree snap-to-bearing-equivalent fix (plus a check that an
    elongated, non-square object's measured yaw is never snapped).

test/test_auto_label.py  (9 tests)
    auto_label.py's pure-geometry pixel-box calculations against
    independently hand-computed expected boxes, plus its relative-pose
    transform against rotations.world_to_body.

test/test_yolo_smoothing.py  (3 tests)
    _TunedBBox3DEstimator (yolo_detection_node.py): the per-object Kalman
    + temporal smoothing, retuned from the YOLO3D library's street-scene
    defaults to this project's tabletop scale.

All seven test files (plus synthetic_depth.py, a renderer, not a test)
are run directly with plain `python3 test/test_X.py` (no pytest/nose
needed) and, as of this refresh, all ~64 tests pass.
